# Caféflow outcomes

- [x] Café profiles: Create a café and manage its business details; save its data between sessions; restrict management to the signed-in café owner.
- [x] Menu and customer ordering: Create and organize menu items with name, photo, description, price, category, and availability. Customers can browse available items, add them to a cart, choose quantities, submit an order, and see a receipt. Persist the order; calculate its unit prices and total from current server-side menu data.
- [x] Item and category discounts: “add a discount option to an item and it's category.” Configure a whole-number percentage discount on an individual menu item and a percentage rule for a café menu category. Show discounted and original prices to customers, in the cart, checkout, receipt, and manager order inbox. Do not stack discounts; an item-specific discount takes precedence over its category rule. Persist discount values and snapshot the effective discount and discounted price when the order is placed.
- [x] User roles: “three kinds of users super admin, cafe admin, and a normal user.” Super Admin can manage every café, café order, and user role; Café Admin can manage only cafés they own, their menus, and their orders; Normal Users can browse menus and place orders. Super Admins can assign account roles. New accounts default to Normal User. Promote the single existing account to Super Admin, as explicitly approved by the user; prevent removing the final Super Admin and prevent self-demotion.
- [x] Café order inbox: Show submitted orders to the café owner, support order-preparation status changes, and provide in-app alerts for new orders.
- [x] Next.js: Build and serve the app with Next.js rather than Vite; preserve customer, manager, auth/OAuth, tRPC API, database, health route, public route manifest, and the application’s existing public links.

## Implementation and validation evidence

Next.js 15 Pages Router catch-all app runs behind the existing Express process. The Express API and OAuth routes remain registered ahead of Next. Shared app providers carry tRPC and React Query; existing Wouter client navigation and public link routes continue working. The production build emits a server-rendered Next route with a client-rendered Caféflow app shell. The eight page patterns remain declared in `client/public/manus-routes.json`, including `/users` for role management.

Discount data is stored in MySQL. The additive `0002_category_discounts` migration adds the default-zero item percentage and category rule table; it was applied successfully. The additive `0003_user_roles` migration preserves legacy admins as Super Admins and installs the three-role enum. The database had one account; that account was promoted to Super Admin as approved. Role assignment is restricted to Super Admins and prevents self-demotion or removal of the final Super Admin. The sample café still has its existing 8 menu items; no orders were written for testing. Public tRPC smoke-check returns those 8 items with both discount fields. New orders compute discount pricing server-side and save immutable list-price, final-price, and effective-percentage snapshots.

All 29 automated tests pass; `pnpm check` passes. Final production build and diff checks are pending. The running Preview health route returns HTTP 200, and `/manus-routes.json` returns the eight current page patterns. No production publication has been requested.
